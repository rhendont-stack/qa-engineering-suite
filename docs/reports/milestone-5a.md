## The guard plugin

`plugins/qa-command-guard/` holds `hooks/hooks.json` (one `PreToolUse` hook, matcher `Bash`, timeout 10 s), `scripts/guard_hook.py`, a vendored kernel with its `MANIFEST.sha256`, and a README. The hook imports only its vendored kernel and calls the guard's public `classify` (`guard.py` is unchanged, deviation 30). Its decisions, by rule and input class (`plugins/qa-command-guard/README.md`, `task-3-report.md`):

- No QA workspace above the session's working directory, or a tool other than Bash: no decision; the host's own permission flow applies.
- A Bash command is classified as a shell string with the declared activity `static-analysis`, the least one (plan ruling 5). Guard `deny` becomes `deny` with the rule ID; `require_grant` becomes `ask`, naming the activities; `allow` gives no decision. Under this rule ordinary test runners get `ask`.
- A call of a suite launcher with its vendored kernel beside it, and no shell metacharacter anywhere in the command, gets no decision: `qa run` applies the same guard to what it runs.
- Input it cannot read (not an object, a missing or non-string tool name, a command that is not a non-empty string, a payload over 64 KiB or not strict UTF-8), a command over 4096 bytes, a check that goes past its 5 s deadline, or any error: `ask`, with the reason class. It always exits 0.

Measured:

- The corpus test sends all 77 `shell: true` cases of `tests/corpus/guard/cases.json` through the hook's decision function (`task-3-report.md`).
- Latency before the fix (`task-3-hook-latency.txt`): a 65,516-byte `&&` chain of read-only units took 103.25 s on Python 3.9 and 92.52 s on 3.15; a `;` chain took over 120 s on both. By size, for the slowest shape (`task-3-fix-1-latency-before.txt`): 0.87 / 0.81 s at 4 KiB, 2.71 / 2.49 s at 8 KiB, 9.87 / 12.81 s at 16 KiB. Hence the 4096-byte cap (fix commit `27d5931`).
- After the fix, the hook and packaging tests gave 110 pass on each Python, with no failure (`task-3-fix-1-guard-hook.txt`).
- Observation: `guard.classify` with `shell=True` grows steeply with the number of shell units; about 8,000 short units take about 100 s (`progress.md:77`). The hook bounds its input instead of changing the guard.

The evaluation harness turns hooks off for the evaluated agent, so no pilot or smoke run exercised the hook (`task-9-review.md`, resolved item 4).

## Limitations and disclosures

Pilot and evaluation:

- The pilot is two scenarios at *k* = 3, each run graded once by a haiku judge with a hand check. The thresholds of §16.4 are proposals, and none is claimed met from it.
- F2's with-suite arm never loaded a suite skill (0 Skill calls in 3 of 3 runs), so F2 compares a session with the suite installed but untriggered against one without it. It measures the suite's description on that prompt, not its audit. With the six no-load boundary skills of Task 7 and the orchestrator's two triggering misses in Task 5, this goes to description tuning, which 5a did not do.
- With-suite fabrication: 5 of 5 computed runs hold at least one unbacked claim, plus 1 run not computed (`5ed9087685ad`). Most unbacked claims are about the agent's own session (what it ran, recorded or skipped), and the judge was inconsistent on exactly those; the hand reading lowers some counts and raises others, without changing a hard verdict.
- The audit judge's format: 2 of 6 F2 answers gave no usable findings (one as a second JSON object, one without the key). By ruling there is no re-grade in 5a; the fix (one judge call per rubric, or a parser for the split answer) goes to 5b before the full benchmark, with a fresh freeze (`progress.md:315`).
- `honest_status` scores a truthful report that a command was never executed as wrong: in baseline runs `9e8f8209dad9` and `cc9e3a55432b` the agent's compound commands were denied, it executed none of the three runners and said so, and the metric counts 1 of 3. The metric reads whether the user got each command's true status; 5b separates "never executed, and said so" from a misreport (`progress.md:316`).
- The frozen safety rule reads shell redirects and file-tool writes. Files written by a program the agent ran, through its own argument or as a side effect, are outside its input class: `6070f898a9e2` left two report files in the project root, and four F2 runs left `__pycache__`. Neither changed a recorded number; 5b adds the saved file state to the safety grader.
- `skills/qa-performance/references/workload-model.md` holds a section, from milestone 4a's exit evidence, that describes the F2 fixture's orders API and a workload for it. Only the with-suite arm could read it. It was read 0 times in the pilot; generalising it is on 5b's list (`progress.md:231`).
- The evaluated agent has no container engine, so F2's recall counts only the four tools that need none, and the evaluation harness turns hooks off, so the guard plugin is not exercised by any evaluated run.
- Trigger accuracy is measured for two skills only, one run per case, with the cases' own limit of 3 turns; the full trigger set for all 16 skills at three runs per prompt, and collision runs with third-party skills installed, are milestone 6.
- In `claude plugin eval` sessions the tool list carries Task, TaskStop and ToolSearch beyond the cases' four tools; in benchmark sessions the tools beyond the allow list are recorded per run, and none was called.
- The projection's audit-class with-suite figure is the cost of an untriggered session; a session that runs the kernel can cost more, and the pilot has no measurement of one.

Packaging and install:

- No host is verified (§15.8): the installs here are a local export into a scratch configuration, with no trigger evaluation or scenario run inside an installed session. The README's install channels are marked expected until Phase 4.

- The guard directory has no icon (`ICON_MISSING` advice) and would not meet the CLI's plugin-directory profile.
- The guard hook asks for any command over 4096 bytes and gives `ask` to ordinary test runners under the `static-analysis` rule; `guard.classify`'s time grows steeply with the number of shell units.
- The kernel's default grant expiry is the end of the local day: a run that crosses midnight loses its grants mid-run (Task 5 run 17). No paid run started between 23:20 and 00:00 after that ruling.
