## [Unreleased]

### Added

- The `qa` kernel, on Python 3.9 or later with the standard library only: workspace, IDs, canonical JSON, hash-chained ledger, derived state, schema validation, process runner, status rules, command guard, authorization, configuration changes and drift detection, secret redaction, and read-only git information.
- Ingestion of JUnit, CTRF and SARIF reports.
- Coverage reports (LCOV, Cobertura XML, JaCoCo XML) as measurement reports: `qa run --report lcov|cobertura|jacoco:PATH` and `qa ingest lcov|cobertura|jacoco FILE --from EXE` record each file's totals and never decide a run's status. A run that declares only measurement reports takes its status from the exit code, and is not a suite run for the gate. A path with `..` or an absolute path outside the project is recorded as given and flagged `path_outside_project`. The parsers are tested against real output from coverage.py, Vitest (V8) and Gradle JaCoCo, produced in containers.
- Mutation-testing reports (mutation-testing-report-schema JSON, versions 1 and 2) as measurement reports: `qa run --report mutation:PATH` and `qa ingest mutation FILE --from EXE` record each file's mutants by status and never decide a run's status. `mutation_score_min` is now evaluable: the score is 100 x (Killed + Timeout) / (Killed + Timeout + Survived + NoCoverage) over the files an accepted override names in `paths`, read from the last mutation report on the target commit from a run that passed or failed; coverage is never read as a score. Tested against real StrykerJS output produced in a container.
- Findings, release gates, Markdown and JSON reports, and checking of the claims a report makes.
- JSON Schemas, gate profiles and command-guard policies.
- The kernel's test suite, repository checks and a GitHub Actions workflow.
- Spine skills: `qa-orchestrator` with the `change` plan template, `qa-test-execution`, `qa-codebase-intelligence` and `qa-reporting`, three Claude Code subagents (`qa-auditor`, `qa-verifier`, `qa-evaluator`), and a skill catalog.
- Container runs: `qa run --container IMAGE@DIGEST` with no network and no bind mount, an optional `--install` step under its own authorization, and a configured container engine.
- `qa plan`, `qa compare`, `qa catalog`, evidence bundle export (`qa report bundle`) and import, `qa finding dedupe`, an executive one-page report, and SARIF as a report format (`qa report render --format sarif`).
- A skill evaluation harness, `tools/run_skill_eval.py`, with a cost ledger and a budget cap.
- `qa report check --ledger [ALIAS=]PATH` (repeatable): a report may cite evidence held in other ledgers, and cite an aliased ledger's IDs as `ALIAS:GATE-001`. Each extra ledger is opened read-only and must verify like `qa ledger verify`. A bare numbered ID (`GATE-`, `RPT-`, `AUTH-`, `PLAN-`, `FND-`) that more than one ledger holds is ambiguous; an `EXE-` or `RES-` ID the ledgers record differently is a conflict. A verdict word is judged against every cited gate and the gate of each cited report, and `expected: TOKEN` marks a token as an expectation rather than a claim.
- `tools/check_repo.py` flags IP and email addresses in `tests/` and `tools/`, and any string listed in an optional, git-ignored `.private-terms` file.
- The [milestone 2 report](docs/reports/milestone-2.md). It records the exit as measured: the Linux kernel legs first failed on tests that need `git` and passed after a test-only guard, the F9 review through the orchestrator needed a scenario correction and then ended `NOT_READY`, which is correct for the whole fixture because one of its runners records a genuine failure (only scenario F9-01, the absent tool, alone gives `INSUFFICIENT_EVIDENCE`, shown by a deterministic run), and the macOS legs were not run locally.
- Analysis and change records in the kernel: requirements (with their source line and provenance), acceptance criteria, assumptions, risks and test cases (`req`, `ac`, `asm`, `risk`, `tc`), typed trace links, `qa trace matrix` with its gaps (`tc_unproven` among them), and `requirements_verified` evaluated by the gate. A requirement inferred or assumed stays unconfirmed until the user's own words confirm it.
- Fixes and revalidation: `qa fix add` and `qa revalidate`, which records FAIL_TO_PASS and PASS_TO_PASS against a base and a fix commit; suite worktrees (`qa worktree add|remove`) and records of the files the suite writes (`qa changes record|list`) under a `write-tests` grant.
- Five skills: `qa-requirements` (with a weak-word scanner for English and Spanish), `qa-test-strategy`, `qa-test-generation`, `qa-regression-guard` (diff impact, a test-weakening scan and a FAIL_TO_PASS helper) and `qa-mutation` (mutmut and PIT converters into mutation-testing-report-schema). `qa-orchestrator` gains the `fix` plan template, literal launcher calls and foreground dispatch; `qa-reporting` gains the traceability matrix.
- `tools/mutate_kernel.py`, which prints the container run that measures the kernel's own mutation score, and `tools/run_skill_eval.py` gains a key helper, generated fixtures with their history, per-case write tools, a saved file state per run and an allow-list that is the agent's Bash boundary.
- The [milestone 3 report](docs/reports/milestone-3.md). It records the exit as measured, with its open items, and the final review fix wave with its re-runs.
- `scripts/git_read.py` in `qa-orchestrator`, `qa-regression-guard` and `qa-mutation`: read-only `log`, `status` and `diff` through the kernel's neutralised git session. The skill texts name no raw git command, and a static test holds that.
- Container runs with a target: `qa run --container` gains `--service IMAGE@DIGEST`, `--service-run SHELL` and `--service-user UID[:GID]` (the run's own service, reachable only on its loopback, network `none`) and `--input PATH` (a file from `.qa/work/` copied in); a tool container that joins its own run's service counts as isolated.
- Pinned tool images for the domain skills in `shared/policies/container-images.json`: Spectral, Schemathesis, Hurl, oasdiff, squawk, PostgreSQL, Semgrep, OSV-Scanner, Gitleaks, ZAP and k6, each by digest with its size; command-guard data rules for ZAP Automation Framework plans, Schemathesis phases (`fuzzing` and `stateful` need `dast-active`), offline OSV-Scanner, Spectral and oasdiff.
- k6 summaries as reports: `qa run --report k6:PATH` reads each threshold as a test, records the metrics labelled `measured` and flags values above the covering `load-test` grant's limits with `load_limit_exceeded`, which turns a would-be pass `inconclusive` (a failure stays `failed`, with the anomaly); `qa ingest k6 FILE --from EXE` attaches a summary to an existing execution, counts its thresholds, records its metrics labelled `measured` and applies the same limit check against the grant that covered that execution. A corpus of the domain tools' real outputs backs the parsers.
- Four skills: `qa-api-testing` (an endpoint inventory with contract drift, Spectral, Schemathesis and Hurl legs), `qa-database` (migration roundtrips on throwaway databases, a squawk-to-SARIF converter, query plans), `qa-security` (Gitleaks, OSV-Scanner, Semgrep with the suite's own rules, a Unicode scan, ZAP baseline and active plans, SARIF triage) and `qa-performance` (k6 scripts from a workload model, a labelled results table). Each skill's text has the agent refuse external and production targets, record a run it cannot start as `blocked`, and cite a recorded run for every tool result it reports.
- Fixtures F2 (an orders API with its OpenAPI contract), F3 (migrations on SQLite with a PostgreSQL variant) and F6 (a loopback-only training lab that its generator writes out at run time with a fresh signing key, run only in containers), with answer keys and `benchmark/graders/recall.py`.
- F7's contract-diff leg runs with the pinned oasdiff image, and `git_read.py show` writes a file from a commit under `.qa/work/`.
- `tools/run_skill_eval.py`: `system_path_only` and `keep_work` per case, and no raw `git` in the base allow-list.
- The [milestone 4a report](docs/reports/milestone-4a.md). It records the exit as measured: deterministic legs per fixture, one evaluated whole-suite run per fixture, the kernel legs and the `report/check` mutation leg, with their open items.
- A self-contained HTML report: `qa report render --format html` writes one page with no script and no external link, under a hash-based content security policy; the Markdown and HTML renderers share their section rows.
- axe-core results as reports: `qa run --report axe:PATH` and `qa ingest axe FILE --from EXE` record each violation as an alert tagged with its WCAG success criterion (`wcag-sc:P.G.N`), and each `incomplete` entry as a `needs-review` note with its own finding. Lighthouse results as measurement reports: `qa run --report lighthouse:PATH` and `qa ingest lighthouse` record the lab scores labelled `measured` with the tool's version; they never decide a status, and a Lighthouse `runtimeError` is refused as `report_invalid`. Report summaries gain `tool_version`, `rules_passed` and `rules_inapplicable`.
- Gate criteria evaluated: `security_scans_executed` reads the classes of scan tools that ran (secrets, dependencies and SAST by default; a `classes` override is validated), `performance_objectives_met` needs an environment of class `staging` or above and reads k6 results, and `migrations_validated` reads the latest structured `db-ephemeral` run. `rollback_validated` stays `NO_EVIDENCE` and says that a rollback rehearsal record arrives through `qa ingest`.
- `qa ci begin` pins a fresh CI workspace to the accepted configuration's hash; a pinned workspace allows only runner-confined activities and refuses grants and verdicts. `qa ci generate --platform github-actions` writes, as a patch, a workflow that re-runs recorded host runs with the launcher the project tracks, actions pinned by SHA from `shared/policies/ci-actions.json`, no environment values and a `timeout-minutes` computed from its steps; it leaves out, with a reason, container runs and runs that never executed, hold redacted text or are not runner-confined.

- Three skills: `qa-frontend` (a static UI scan, Playwright checks at three viewports, axe-core and Lighthouse legs, and a WCAG 2.2 A and AA table that marks every criterion no tool decided), `qa-release` (a workflow scan, a release-readiness check, actionlint and zizmor legs, and the CI re-execution job through `qa ci`) and `qa-mobile` (a static check of Android and iOS configuration; dynamic checks are listed with a remediation and never run). ### Fixed

- The traceability matrix gives a row its run's status when that run did not conclude with a pass or a fail, and `requirements_verified` and `no_blocked_critical` count only runs on the target tree.
- A report the kernel renders now passes `qa report check`: the gate's details no longer put a bare status word next to `AC-` and `TC-` IDs.
- A declared JSON report is no longer made invalid by redaction: it is redacted per key and value and stored re-serialised when redaction changes it.
- `qa changes record --kind created` on a repository git cannot read now needs the approval a modification needs, instead of passing; a `files` record stores `tracked` and `git_unknown` only when true.
- The test map read and the matrix write use the canonical JSON reader and writer, which refuse duplicate keys. Kernel messages no longer cite sections of unpublished documents.
- `tools/mutate_kernel.py` refuses to overwrite a different `setup.cfg` without `--force` and says the file must not be committed.
- `qa-regression-guard`'s FAIL_TO_PASS helper prints a revalidation command only when the fix's findings name the defect test, and otherwise reports the fix unverified and exits 1.
- `qa-orchestrator` follows a delegated skill's own command forms and writes only what that skill names; it and `qa-regression-guard`, `qa-mutation` and `qa-test-generation` return to the project root after a worktree `cd`. Only template skills are plan steps. `qa-test-generation` records the user's trust approval, `qa-test-strategy` maps a medium risk to criticality `normal`, and `qa-mutation` says what the gate reads for its score.
- Milestone 4a carry-overs: `unicode_scan` labels its NUL-as-space reading on its own, `query_trace` reports a driver that fails to import as one JSON object, `endpoint_inventory` lists a contract or source file over 2 MiB as unreadable, the OSV ecosystems follow the detected lockfiles, and the graders read each saved run's own `config.json` for trust.
- `qa-performance`'s results table reads load-limit lines from ingested k6 entries as well as from the run's own limitations.
- `qa-database` names the container route for a roundtrip when the project is not trusted, instead of describing a host roundtrip as allowed without trust.

- `qa-orchestrator` runs the evaluation step before it answers, also when it works in its own context.

### Security

- The kernel's git reads no longer run a filter or diff program that a repository configures for itself (its `.git/config`, an included file, `config.worktree` or a submodule); a user-level driver such as git-lfs still applies. The diff hash is computed as a stream.
- `tools/run_skill_eval.py` deletes each run's working copy after saving its `.qa/` state, and redacts hex and base64 forms of the API key as well as the key itself.
- An `ssh` container engine runs with `LogLevel=ERROR`, so login banners stay out of the logs.
- The skills' git reads go through `git_read.py` and the kernel's neutralised session instead of raw `git status`, `git log`, `git diff` or `git show`, which read the repository's own configuration and could start a program it names.
- Redaction of a declared JSON report keeps its strength: the parsed document's keys and values are redacted with the ledger's patterns, and a report whose secrets are not all found that way keeps the byte-level redaction.
- An unreadable repository no longer lets `qa changes record --kind created` skip the approval for a tracked file.
- A host run of any activity except `static-analysis` needs `project.trust`: in a project that is not trusted it is refused as `not_authorized` before any standing authorization or grant is read, and the refusal names both routes (trust recorded from the user's own words, or a container run). Milestone 4a let a grant stand in for trust.
- `tools/run_skill_eval.py` gives its CLI probes a fresh temporary `HOME` and `CLAUDE_CONFIG_DIR`, and its evaluated agent the switches that turn telemetry and non-essential traffic off. Before this fix the probes ran with the caller's real `HOME`; whether they read or wrote the caller's Claude Code configuration is not known.
- The evaluation harness can run a scenario with the suite installed as a plugin: the staged copy holds no README, evaluation cases or answer material, the agent may load only the suite's own skills, and an output directory outside `.superpowers/` is refused.
